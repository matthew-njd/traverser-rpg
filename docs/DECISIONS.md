# Decisions Log

- 2026-07-25 — T1: content data (enemy stats, moves, items, gear, drop rates, thresholds) lives in seeded Postgres tables served to the client as a versioned bundle, rather than as client-side JSON. Reason: single transcription point for GDD tables, assertable against the fixtures by a real test, FK integrity for player rows. The client-side battle engine still works offline off the cached bundle.
- 2026-07-25 — T1: `xp_curve` is seeded as 60 precomputed rows rather than evaluating `round(100 × L^1.05)` at runtime. Reason: .NET banker's rounding and JS `Math.round` disagree at exact halves, and client/server must never disagree about a level-up.
- 2026-07-25 — T1: two ID families used in the schema are not yet in `traverser-data-manifest.md` — zone-gate keys (`gate_cyclops`, `gate_cerberus`, `gate_fenrir`, `gate_jormungandr`, `gate_griffin`, `gate_cacus`) and the expanded gear keys implied by the manifest's `gear_{slot}_{tier}` pattern (12 concrete keys). Add both to the manifest before M0 seeding.
- 2026-07-25 — T1: `gear_move.source_gear_id` dropped in favour of a single direction (`gear_def.grants_move_id`), avoiding a circular FK. The manifest's reverse mapping is a lookup, not stored.
- 2026-07-25 — housekeeping: this file was UTF-16LE with mangled `×`/`—` characters; rewritten as UTF-8. Content unchanged.
- 2026-07-25 — T2: the server is the progression authority (XP, level curve, Leagues, gate state, encounter RNG); the client keeps battle resolution only. Reason: progression is cumulative and irreversible, so the level curve is implemented once, next to `xp_curve`. Does not change the sanctioned client-side-battle trim.
- 2026-07-25 — T2: sync issues encounter *grants* rather than delivering battles — enemy and zone resolved server-side, counted against the 5/day cap at issue time, spent by the client whenever (online or not). Reason: reconciles server-owned encounter RNG with fully-offline play, since the API is off between sessions by design.
- 2026-07-25 — T2: `client_delta_id` is a UUIDv7 minted when the delta is created on-device and never regenerated on retry. Explicitly **not** a content hash or `(date, source, steps)` tuple — two legitimately identical deltas would collide and one would be silently dropped, losing real steps.
- 2026-07-25 — T2: additive merge (`col = col + delta`) is mandatory for steps, tier minutes, and all XP/lifetime totals, which are monotonically non-decreasing on the server. Last-write-wins is retained deliberately for settings, equipped gear, skill loadout, and `hr_session` tier minutes, where the newest value is the truth.
- 2026-07-25 — T2: guest identity is a device-generated `player_id` plus an opaque long-lived bearer token. Reason: T6 exposes the API over Tailscale, so an unauthenticated write surface isn't acceptable even single-player. Real auth later is additive (`auth_identity`), no endpoint changes.
- 2026-07-25 — T2: multi-device sync (GDD 11 §11) remains open and unsolved. Additive-over-ledger merge means concurrent devices can't corrupt totals, but per-day streak/grace evaluation would need a design pass. Seam noted, not built.
- 2026-07-25 — T3: **GDD 10 deviation.** A birth-year field is added to the Screen 3 character-creation step. Reason: GDD 1 §2.2 requires `HRmax = 220 − age` and the locked eleven-screen onboarding never collects age — a gap between two locked specs. Health Connect exposes no dependable age/DOB record type. Editable later in Settings; changes apply to future reads only and never recompute past days.
- 2026-07-25 — T3: HR sessions are segmented from the heart-rate sample timeline (GDD 11 §8.1's 10-minute-drop rule), **not** from Health Connect `ExerciseSession` records. Reason: the GDD defines a session in terms of elevated HR, not a workout the player remembered to start; anchoring to exercise sessions would award nothing for a brisk unlogged walk. Cost is the loss of a provider-issued session ID.
- 2026-07-25 — T3: consequently `hr_session.external_session_id` takes tech-01 §7's pre-authorised fallback, encoded as `"hr:{started_at epoch seconds}"` so the existing `unique (player_id, external_session_id)` index enforces the `(player_id, started_at)` key. **No schema change.** A local ledger freezes each session's `started_at` so backfill can't shift the ID.
- 2026-07-25 — T3: tier minutes are derived by 1-minute buckets scored on the mean BPM of the samples in each bucket; minutes with no samples are untiered. Reason: integer minutes fall out of the algorithm rather than being rounded in at the end, the unit matches GDD 1 §2.2's per-minute rates exactly, and every case is fixture-assertable. Spike probe 1 may replace this with sample-interval weighting if real sampling proves too sparse.
- 2026-07-25 — T3: daily steps are read via `aggregateGroupByPeriod` rather than raw `readRecords`, specifically because Health Connect de-duplicates overlapping step contributions from multiple origins (phone + watch) during aggregation. Doing that reconciliation ourselves is out of sanctioned scope, and summing raw records would double-count every day for any player wearing a watch.
- 2026-07-25 — T3: the client mints step and HR-minute deltas as the **difference** over a persisted per-date high-water mark, never as the day's total, because T2 §6.1 merges additively and the read window re-reads days already reported. A downward provider revision mints nothing and does not lower the mark.
- 2026-07-26 — **spike/health-connect run on a Pixel 9 (Android 16), data source `com.fitbit.FitbitMobile`.** Findings below; environment: `react-native-health-connect` 3.5.3, Expo SDK 57, local `expo run:android` dev build. Probe numbering per T3 §12.
- 2026-07-26 — T3 §3 **correction (probe 6): a read without permission throws, it does not return empty.** Verified for both types: `HealthConnectException: java.lang.SecurityException: Caller requires android.permission.health.READ_STEPS/READ_HEART_RATE`. T3 §3's claim that "a revoked read returns an empty result, not an error" is wrong. The read path needs a catch mapping the exception to the banner state — probe 6's stated fallback. The distinction T3 draws between empty-and-unpermissioned vs. empty-and-sedentary is now trivially safe: the former can't produce an empty result at all. *(Tested via denial; revoke-after-grant not separately tested, same native path.)*
- 2026-07-26 — T3 §3 **addition: `initialize()` is per-process and must precede every read**, not just onboarding. Changing permissions in Health Connect settings restarts the app process, after which every call fails with "Health Connect client not initialized". T3 §3 currently says only `getGrantedPermissions` re-runs each foreground; `getSdkStatus` → `initialize` must join it.
- 2026-07-26 — T3 §3 confirmed: **re-requesting after a denial is a silent no-op** — `requestPermission` returns `[]` and no dialog appears. The `openHealthConnectSettings()` deep link is mandatory, exactly as specified.
- 2026-07-26 — T3 §3 **addition: granting Steps also silently grants `StepsCadence`**, a record type never requested and absent from the manifest. `getGrantedPermissions` can therefore return more entries than were asked for; it must be checked by exact `recordType` match, never by array length or index. Partial grant otherwise behaves as specified (probe 7 passes — Steps granted, HeartRate denied, reported independently).
- 2026-07-26 — T3 §5.2 **confirmed unchanged (probe 1).** Fitbit HR sampling is dense: median inter-sample gap **2s** (min 1, max 3), zero gaps over 60s. Whole-minute bucketing is viable; the sample-interval-weighting fallback is **not** needed and fixtures stand.
- 2026-07-26 — T3 §4.2 **confirmed (probe 5).** `aggregateGroupByPeriod` slices on **local** midnight: at UTC-4 a bucket came back `2026-07-26T00:00 → 00:11:42`, not the 20:00 a UTC slice would give. Mechanism: the library parses the filter with `Instant.parse(x).atZone(systemDefault()).toLocalDateTime()`. **Consequence for M1:** the time range filter must be given a **UTC instant string** (`toISOString()`); a local-naive string throws `Text '...' could not be parsed at index 19`. The library does the local conversion itself.
- 2026-07-26 — **new, not anticipated by T3: reads are paginated and must follow `pageToken`.** A 48-hour HeartRate read returned exactly **1000** records — the default `pageSize` cap — with `pageToken` present. Any read assuming one call returns the full window will silently truncate. T4 owns this.
- 2026-07-26 — **new, not anticipated by T3: Fitbit writes HR as ~one record per minute, not one per workout.** Record durations min 25s / median 57s / max 59s, averaging 25.6 samples each. The densest single record is 32 samples over 59 seconds. T3 §6 session identity must stitch hundreds of adjacent records into a session; no single record ever represents one. Reinforces the §5.2 decision to segment from the sample timeline rather than from provider records.
- 2026-07-26 — T3 §6 confirmed (probe 3): `metadata.id` was **stable** across app restarts and a permission revoke/re-grant cycle (same UUID both runs). Diagnostics can rely on it; the ledger still keys on derived session identity per spec.
- 2026-07-26 — **historical depth on this device is ~30 days**, not longer: 197 step records at 30d ago, 0 at 90d, 0 beyond (same shape for HeartRate). Comfortably clears T3 §4.1's 72-hour window, but GDD 11 §3.2's grace lookback must not assume more than ~30 days of recoverable history.
- 2026-07-26 — **T3 §4.2 VERIFIED (probe 4): `aggregateGroupByPeriod` does de-duplicate across origins.** A walk carrying the phone and wearing the watch produced two independent writers — `com.fitbit.FitbitMobile` (348 steps) and the phone's own sensor `com.android.healthconnect.phone.j8803…` (253 steps) — for a raw sum of 601 across 11 records, against an aggregate of **373**. 228 duplicated steps were discarded by Health Connect. Summing raw records would have inflated the day by ~60%. The single-origin fallback is not needed and `aggregateGroupByPeriod` stands as specified. *(Two earlier attempts were inconclusive and are worth remembering as method notes: with the phone plugged in and stationary only one origin appears, and before the watch syncs the two origins' contributions are too small and disjoint to collide.)*
- 2026-07-26 — **the phone writes steps to Health Connect independently of Fitbit**, under `com.android.healthconnect.phone.<hash>`. Multi-origin is the normal steady state on this device, not an edge case, which is what makes §4.2's reliance on aggregation load-bearing rather than defensive.
- 2026-07-26 — **T3 §12 probe 2 (backfill latency) remains UNCHARACTERISED.** Observed only that a read taken minutes after a walk showed 23 steps while the true figure was ~373 — the watch's contribution had not yet reached Health Connect. A manual Fitbit sync was then triggered out of impatience, so **whether automatic sync would have delivered it, and how quickly, was not tested.** The finding that matters is directional and sufficient for M1: a read taken shortly after activity can understate the day severely. T3 §4.1's 72-hour re-read window and §8 idempotency already absorb this, and the §4.2 high-water-mark design already assumes a fresh read is never final for the current day. Measuring the actual interval is an opportunistic M1 task, not a blocker.
- 2026-07-26 — minor: `aggregateGroupByPeriod` returns `dataOrigins: []` even when a raw read of the same window reports `com.fitbit.FitbitMobile`. Do not use the aggregate result's `dataOrigins` for provenance; use `readRecords` metadata if provenance is ever needed.

- 2026-07-26 — T5: **the damage formula floors twice, not once.** GDD 2 §7's formula line reads as a single trailing `floor()`, which yields 27 on the super-effective worked example — but GDD 2 §7's own worked example, and fixtures §2, both say **26**, arrived at by flooring the quotient first (`floor(1950/144) = 13`) and then multiplying. Fixtures are the oracle (CLAUDE.md), and the double-floor reading is corroborated by every deterministic value in fixtures §3. Normative pipeline: `base = floor((Power × Atk)/(Def × 8))`, then `max(1, floor(base × surge × type × rend × fortify × weaken × crit × random))`. This is a correction to GDD 2 §7's *notation*, not to its intended behaviour. Note the trap: the two neutral fixture rows pass under either implementation, so only the SE row distinguishes them — pinned by a dedicated test (T5 §11.2).

- 2026-07-26 — T5: **the client rolls loot; the server records it.** `drop_rate`/`enemy_drop_pool` are already client-cached content (T1 §7), and rolling server-side on battle ingest would leave a boss drop nonexistent until the next sync — days, with the API off by design (T2 §1.2) — breaking GDD 13 §6.3's victory-screen Reveal Card. **Requires T2's battle payload to grow a `drops` array**, ingested under the existing `client_battle_id` conflict guard. The tutorial test runs on an empty `ScriptedRng` so any draw throws.

- 2026-07-26 — **T2 amended by T5: the battle payload now carries a `drops` array** (new T2 §4.1). Gear/trinket drops carry their frozen `bonus_primary` and `level_at_drop` — the one place the client supplies a value the server would otherwise derive, which is deliberate because tech-01 §4 freezes the bonus at drop time (re-deriving it server-side would be the bug). - 2026-07-26 — **GDD 3 and GDD 4's closed "the ×3.0 ceiling never approaches a one-shot" is FALSE for a Favor-specialized build** (fixtures §10.9, verified against real roster stats). Surge+SE at ×3.0, no crit, best SE move for the level: one-shots Satyr at L6 (66 vs 23 Vigor) and L15 (96 vs 45), and Cyclops at L10 (75 vs 60) and L15 (90 vs 82). At the absolute ×4.95 ceiling (×3.0 + crit + roll 1.10) **every enemy in the game one-shots, bosses included** — Cacus L60 takes 188 against 154 Vigor. A *balanced* build matches the GDD's published turn counts closely (Cyclops L15 in 5 SE hits, Cerberus L15 in 6), which is why the original balance modelling missed it: the gap is build specialization, not the formula. **T5 changes nothing** — the formula is locked and implemented as written, and T5 §11.5 asserts a bounded-damage property (`1 ≤ dmg ≤ floor(base × 4.95)`) instead of the survival property, which is not true. - 2026-07-26 — T6: **the phone reaches the API over Tailscale via `tailscale serve --bg --https=443 http://127.0.0.1:8080`, and Compose binds `127.0.0.1` only.** Confirmed against current Tailscale docs: Personal plan is free (6 users, unlimited user devices, 50 tagged), MagicDNS plus admin-console HTTPS gives a real Let's Encrypt cert for the machine's `*.ts.net` name. Reason for Serve over a raw `100.x` tailnet IP: Android has blocked cleartext HTTP by default since Android 9, so a plain-HTTP endpoint would need a `networkSecurityConfig` exemption — and since `android/` is generated and not committed (T4 §1.1) that exemption would have to become a permanent hand-written config plugin. `--bg` is load-bearing: without it Serve dies with the terminal and needs manual restart after every reboot. Tailscale **Funnel** and router port-forwarding are both rejected as public exposure. Enabling HTTPS publishes machine and tailnet DNS names to a public certificate-transparency ledger — inherent to Let's Encrypt, mitigated by naming the host something uninteresting. - 2026-07-26 — T6: **managed cloud Postgres is rejected for the life of the project**, Supabase named as the concrete instance of the pattern. Both resolve by paying, violating the $0 constraint. - 2026-07-26 — T6: **Postgres backups are `pg_dump -Fc` to local disk plus an already-synced OneDrive/Drive folder, 7 daily / 4 weekly / 12 monthly, mandatory from M1 — before the first real step sync, not after.** Off-machine matters because a dead PC takes every same-machine copy. Restore drill (`pg_restore` into a scratch DB, spot-check, `dropdb`) runs at M1 and M5 — an untested backup is not a backup. - 2026-07-26 — T6: **a stable out-of-tree release keystore is mandatory, not good practice — and this is a consequence of T4 §1.1 that T4 does not state.** `expo prebuild --clean` regenerates the *debug* keystore, so anything signed with it has a silently-changing signing identity; Android refuses to update-install across a key change, the only way forward is uninstall, and per T4 §6.5 uninstall destroys `player_id` and the bearer token unrecoverably. Release artefact is an **APK**, not an AAB (AAB cannot be sideloaded).
- 2026-07-26 — T6: **backing up Postgres alone is not restorable-to** — `player_id` and the token live only in app storage (T4 §6.5), so a restored database has no client able to claim it. Opened as T6 §13.1 rather than decided silently. **Recommendation: a manual `player_id`/token export-and-restore path at M1**, alongside the backup job — a screen, a file, and a branch in registration. The recovery-code alternative arrives with real auth (T2 §8) and should not be built before it. T4 §15 deferring "account recovery after uninstall" was right as a *feature* decision but leaves T6's backup deliverable incomplete.
